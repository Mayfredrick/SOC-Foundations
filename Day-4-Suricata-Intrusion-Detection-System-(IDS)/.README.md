## 1. Suricata Fundamentals

Suricata is an open-source network threat detection engine that can operate as an intrusion detection system (IDS), intrusion prevention system (IPS), and network security monitoring tool.

Suricata uses rules and signatures to identify network traffic that matches known patterns or detection conditions.

### Suricata vs. Zeek

| Tool | Primary purpose |
|---|---|
| Suricata | Detects potentially suspicious network traffic using rules and signatures. |
| Zeek | Analyzes network activity and produces structured logs and protocol metadata. |
| Strelka | Analyzes files and identifies patterns that may require further investigation. |

- Suricata rule engine status: **OK**

I initially ran the documented test request:

"""bash

"""

The request failed with a DNS resolution error. When I queried "testmynids.org", the DNS resolver returned "NXDOMAIN". However, "nslookup github.com" returned an IP address, and querying "testmynids.org" through "8.8.8.8" also returned "NXDOMAIN".

This showed that general DNS resolution was working for the domain I tested, while the specific test hostname was not resolving through either resolver.

I also ran:

"""bash

"""

The GitHub connection appeared in Security Onion Hunt, confirming that the sensor was receiving or processing at least some network traffic.

The test generated multiple Suricata alerts and one Strelka alert.

### Analysis

The alert identified SMB-related activity involving the IPC$ share over TCP port 445. The signature indicated that the traffic matched a configured Suricata detection rule.

I checked the source and destination IP addresses against my lab VMs. Neither address belonged to my VMs, which used different subnets.

Because the alert appeared during the "so-test" exercise, the traffic was likely associated with replayed sample data rather than a live connection between my own VMs.

The alert alone does not establish that the access was unauthorized or that a system was compromised. Further investigation would be needed to determine the activity's context.

## 5. Strelka Alert Investigation

### Alert details

| Field | Observed result |
|---|---|
| Alert name | "SUSP_DOUBLE_Base64_Encoded_Executable" |
| Priority | "3" |
| SID | Not provided |
| Source/destination IP | Not provided |
| Timestamp | "2026-10-09T14:18:45.204Z" |
| SHA-256 comparison | Matched the downloaded Raspberry Pi ISO, according to my comparison |
| PE machine type | "i386" |
| PE primary file type | "APP" |

### Analysis

Strelka produced an alert associated with a suspicious executable pattern. The alert description and metadata indicated executable-related characteristics.

I compared the SHA-256 value displayed in the alert with the hash of a Raspberry Pi ISO I had downloaded earlier. The hashes matched, linking the alert record to the same file hash.

However, the alert does not prove that the ISO is malicious. A detection rule identifies a pattern that warrants investigation; it is not a definitive malware verdict.

The "i386" and "APP" fields describe executable-related metadata reported by Strelka. I would verify the exact file or scan object to which these fields apply and compare the ISO's hash with the checksum published by its official source.

### Follow-up investigation

- Verify the ISO came from an official source.
- Compare its SHA-256 hash with the publisher's published checksum, if available.
- Review the full Strelka scan results and the rule description.
- Investigate the exact file associated with the executable metadata.
- Use reputable malware-analysis tools in an isolated environment if further analysis is needed.

No confirmed malware finding was established during this lab.

## 6. Alert vs. Security Incident

A detection alert indicates that a rule or detection mechanism identified activity that warrants review. A security incident is an event or set of events assessed as requiring a security response.

Not every alert is malicious. Analysts must validate the evidence, understand the environment, investigate the activity, and determine whether escalation or containment is necessary.

## 7. Troubleshooting Approach

When the expected Suricata alert did not appear, I:

1. Checked the Suricata rule engine status.
2. Confirmed that rule SID "2100498" was present.
3. Tested DNS resolution using different domain names.
4. Queried the test hostname through the default resolver and Google DNS.
5. Confirmed that a GitHub connection appeared in Hunt.
6. Ran "sudo so-test" according to Security Onion's documentation.
7. Reviewed the alerts generated by the test.

This process helped me separate a failed test hostname from the overall status of the Suricata service.
